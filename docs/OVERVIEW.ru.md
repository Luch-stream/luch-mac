# Luch — отправитель для macOS

Отправитель Luch для macOS: тот же протокол, тот же приёмник на телевизоре или телефоне, другая
платформа под капотом. Говорит на v0 ровно так, как описано в PROTOCOL.md, поэтому на стороне
приёмника ничего менять не нужно — все новые поля протокола опциональны.

Репозиторий: `Luch/luch-mac`, ветка `main`. Родственные: `Luch/luch-linux` (отправитель для Linux) и
`Luch/luch-android` (приёмник).

## Зачем это

У Luch есть отправитель для Linux и приёмник для Android. Мак не мог отдавать картинку: KMS, VA-API и
PipeWire — не его APIs. Здесь тот же протокол и тот же стиль — без копий в горячем пути, IDR только по
запросу, сокеты привязаны к интерфейсу — но на ScreenCaptureKit и VideoToolbox.

| Часть | Что использует |
|---|---|
| Захват | ScreenCaptureKit: дисплей, NV12 video range, курсор в кадре, размер под клиента |
| Звук | Системный звук ScreenCaptureKit → libopus, 48 кГц стерео, CBR 128 кбит/с, кадры 20 мс |
| Видео | VideoToolbox H.264 или HEVC, real time, без B-кадров, IDR по запросу, Annex-B, SPS/PPS перед каждым IDR |
| Поиск | DNS-SD (Bonjour); каждый сокет привязан к интерфейсу, на котором найден приёмник |
| Управление | Unix-сокет + JSON — замена D-Bus у Linux-отправителя |

## Что сделано

**Протокол и сеть.** 24-байтный заголовок, шарды по 1376, JSON-канал управления, Bonjour-обнаружение
с сохранением индекса интерфейса. Контрольный канал и оба медиа-сокета биндятся к этому интерфейсу, так
что полный туннель VPN не утащит поток.

**Выбор кодека со взвешенной оценкой.** Приёмник рассказывает в `welcome`, какие у него декодеры, как
быстро каждый измерился, какой максимальный размер он принимает и какая у него форма экрана. Отправитель
считает оценку для каждого кодека, который умеют обе стороны:

- HEVC — за битрейт при том же качестве (примерно на четверть меньше), H.264 — за совместимость;
- кодек, который приёмник назвал самым быстрым, получает **3 мс форы по времени**, а не фиксированный
  бонус, поэтому при равном времени декодирования HEVC всё равно выигрывает по битрейту;
- время декодирования, **измеренное в реальной сессии**, важнее бенчмарка приёмника (тот меряет ядро
  декодера, а не путь до экрана), и запоминается по паре «приёмник + кодек»; неправдоподобные замеры
  отбрасываются;
- лимит декодера — последнее слово, применяется пропорционально.

`luch caps "<приёмник>"` печатает оценки, их слагаемые, источник замера и итоговый план.

**Размер и качество — два независимых рычага.** Размер выбирает, чья геометрия побеждает: `source`
(аспект Mac), `fit` (аспект Mac в пикселях клиента), `average`, `client` (экран клиента, рабочий стол
обрезается). На телефоне 20:9 режим `fit` сохраняет весь рабочий стол — без растяжения и без обрезки.
Качество — пресет: `auto` (ровно то, что сообщил клиент), `720p`, `1080p`, `2K`, `4K`; декодер без
поддержки 1080p60 ограничивает поток 30 fps, а декодер без 4K ужимает размер пропорционально.

**Состояние клиента показываем, но не навязываем.** `welcome.hw.device` и посекундные `stats` несут
батарею, заряд, температуру и thermal headroom. Отправитель их показывает — `🔋 on battery`, `🌡0.62`,
`🔥0.21` — и никогда не снижает качество за спиной пользователя; пресеты выше 720p получают пометку
`drains the battery faster`, пока клиент работает от батареи.

**Keepalive под таймаут приёмника.** ScreenCaptureKit отдаёт кадры по изменениям и на статичном рабочем
столе выдаёт ~1 fps. Поэтому отправитель повторяет последний access unit: P-кадры 2 раза в секунду,
IDR реже — оба интервала заведомо внутри 15-секундного лимита тишины приёмника; инвариант закреплён
тестом. Повтор несёт исходную задержку «захват → отправка», поэтому среднее у приёмника не врёт.

**Тёплый фильтр для ночного просмотра.** Слайдер в меню сдвигает синюю хрому вниз, а красную вверх
прямо в плоскости NV12 перед энкодером, с весом по яркости — тёмный интерфейс остаётся нейтральным, а
не зеленеет. Один проход по плоскости половинного разрешения: меньше миллисекунды, без Core Image и
лишних буферов; применяется на ходу.

**Меню-бар и CLI.** Выбор приёмника, живая статистика (оценка задержки, host, RTT, decode, батарея,
нагрев), подменю Warm picture, Quality, Size, Codec, Bitrate, Display и автозапуск при входе. Плюс
`luchctl` поверх Unix-сокета и `luch` — движок без приложения, с `--preset`, `--size-mode`, `--codec`,
`--profile`, `--frame-ms`, `--warm`, `--synthetic`, `--ip`.

## Приёмник

В `receiver/` лежит патч к `luch-android` с изменениями на стороне клиента, которые делают связку лучше:
`DeviceState` (батарея/заряд/нагрев/headroom, только по событиям), расширенный оверлей и значок `🔥`,
исправление жизненного цикла (переключение кодека занимает ~114 мс вместо чёрных экранов на секунды),
letterbox вместо растяжения, запрос 120 Гц, `max-num-reorder-frames`, взвешенный `prefer` и описание
новых полей в `PROTOCOL.md`. С отправителем из этого репозитория работает и немодифицированный приёмник.

## Проверено

- `swift test`: **27 тестов** — заголовок, сборка шардов, `OpusHead`, нарезка Opus-кадров, AVCC→Annex-B,
  границы keepalive, веса кодеков, пресеты качества, батарея/нагрев, тёплый фильтр;
- `Tools/fakerecv.py` (обратный `testsend.py` приёмника): 864/864 кадра, 0 потерянных шардов, проверки
  заголовка, Annex-B и SPS/PPS-перед-IDR проходят, ffmpeg декодирует чисто;
- Apple M4 Max → Samsung S24+ по Wi-Fi, HEVC 1662×1080@60: захват + кодирование + отправка **2–5 мс**,
  56–58 fps, RTT 7–10 мс, декодирование у приёмника **5–11 мс**;
- H.264 на том же телефоне — **75–85 мс** живьём, хотя его собственный бенчмарк говорит 12.7 мс. Поэтому
  измеренное время декодирования и важнее бенчмарка;
- переключение кодека в меню: новый декодер поднимается за **114 мс**, картинка не гаснет.

## Чего нет

- захвата отдельного окна (`SCContentFilter(desktopIndependentWindow:)`) — следующий шаг;
- виртуального дисплея / режима расширения — публичного API нет, нужен `CGVirtualDisplay`;
- обратного канала ввода (тач, клавиатура) — зарезервирован в PROTOCOL.md §6, не реализован ни на одной
  стороне;
- приёмник на дисплее с высокой частотой: панель телефона умеет 120 Гц, но система не отдаёт их
  приложению, поэтому экран обычно добавляет до одного периода кадра (~8 мс на 60 Гц), и это не входит
  в оценку задержки.

## Как собрать

```sh
swift build -c release
./Tools/make-app.sh                        # Luch.app рядом с пакетом
SIGN_ID="<your code-signing identity>" ./Tools/make-app.sh   # стабильная подпись: TCC не попросит заново
open .build/Luch.app
```

macOS спросит Screen Recording и доступ к локальной сети. Разрешение Screen Recording привязано к
подписи: при ad-hoc сборке его придётся выдавать заново после каждой пересборки.

## Мелочи, которые стоит знать

- 5-мс кадры Opus трещат на Android: буфер `AudioTrack` у приёмника — около четырёх кадров (20 мс),
  поэтому джиттер Wi-Fi их рвёт. 20 мс (50 пакетов/с) показали себя лучше всего и стоят по умолчанию;
  `--frame-ms` меняет на ходу.
- VideoToolbox не всегда ставит `kCMSampleAttachmentKey_NotSync`, поэтому IDR определяется по битстриму
  (NAL type 5), а параметры из format description подставляются перед каждым IDR — приёмник
  конфигурирует декодер без `csd-0`.
- Тёплый фильтр проходит плоскость хромы один раз за кадр: заметно меньше миллисекунды на 1080p.
